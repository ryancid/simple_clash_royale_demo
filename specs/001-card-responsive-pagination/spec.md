# Feature Specification: 卡片頁面響應式分頁優化

**Feature Branch**: `001-card-responsive-pagination`
**Created**: 2025-12-06
**Status**: Draft
**Input**: User description: "修改這個頁面，讓卡片數量符合一頁一排，無論使用者的頁面是大是小，除了最後一頁無法填滿最後一排外，需要讓每頁填滿。需測試目前頁面是否有問題，key可先拿.env.local的測試。需看卡片的回傳資料設計相關功能"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 響應式卡片網格佈局 (Priority: P1)

使用者造訪卡片列表頁面時，無論使用何種裝置（手機、平板、桌機）或瀏覽器視窗大小，都能看到整齊對齊的卡片網格。每一排都應該被完整填滿，不會有參差不齊的情況（除了最後一頁的最後一排可能不滿）。

**Why this priority**: 這是最核心的使用者體驗改善，直接影響所有使用者的視覺體驗。良好的網格佈局能讓使用者快速瀏覽和找到想要的卡片。

**Independent Test**: 可以透過調整瀏覽器視窗大小（從手機尺寸到桌面尺寸）來測試，驗證每一排的卡片數量會根據視窗寬度自動調整，且都完整對齊。

**Acceptance Scenarios**:

1. **Given** 使用者在手機上開啟卡片列表頁面，**When** 頁面載入完成，**Then** 每一排顯示固定數量的卡片（例如 3-4 張），且每排的卡片數量一致
2. **Given** 使用者在桌面瀏覽器開啟卡片列表頁面，**When** 頁面載入完成，**Then** 每一排顯示更多數量的卡片（例如 6-8 張），且每排的卡片數量一致
3. **Given** 使用者正在瀏覽卡片列表，**When** 調整瀏覽器視窗寬度，**Then** 卡片網格會即時重新排列，每排卡片數量自動調整以填滿視窗寬度
4. **Given** 使用者切換到不同裝置（手機轉橫向、平板），**When** 頁面重新渲染，**Then** 卡片網格適應新的螢幕方向，保持每排填滿

---

### User Story 2 - 智慧分頁計算 (Priority: P2)

當卡片依照響應式網格排列後，每一頁顯示的卡片數量應該是「每排卡片數量」的倍數，確保每頁的所有排都是填滿的（除了最後一頁的最後一排可能不滿）。使用者在不同裝置上看到的每頁卡片數量會不同，但都能確保整齊的排列。

**Why this priority**: 這是對 P1 的增強，確保分頁邊界不會切斷某一排的卡片，進一步提升使用者體驗。

**Independent Test**: 在不同螢幕尺寸下，點擊「下一頁」按鈕，驗證每一頁的最後一排都是完整的（除了總數的最後一頁）。

**Acceptance Scenarios**:

1. **Given** 使用者在桌面瀏覽器上每排顯示 6 張卡片，**When** 檢視第一頁，**Then** 該頁顯示的卡片總數是 6 的倍數（例如 24 張 = 4 排）
2. **Given** 使用者在手機上每排顯示 3 張卡片，**When** 檢視第一頁，**Then** 該頁顯示的卡片總數是 3 的倍數（例如 21 張 = 7 排）
3. **Given** 使用者正在瀏覽第一頁，**When** 點擊「下一頁」按鈕，**Then** 新頁面的卡片仍然保持每排完整填滿
4. **Given** 使用者調整了視窗寬度導致每排卡片數量改變，**When** 重新計算分頁，**Then** 當前頁面仍保持每排填滿的狀態

---

### User Story 3 - 分頁導航體驗優化 (Priority: P3)

使用者在瀏覽多頁卡片時，能清楚知道當前在第幾頁、總共有幾頁，並能快速導航到想要的頁面。

**Why this priority**: 提升使用者在大量卡片中導航的便利性，但對核心功能（卡片展示）的影響較小。

**Independent Test**: 點擊分頁按鈕，驗證頁碼顯示正確，且按鈕的啟用/停用狀態符合邏輯。

**Acceptance Scenarios**:

1. **Given** 使用者在卡片列表頁面，**When** 檢視分頁控制區域，**Then** 能看到當前頁碼和總頁數（例如「第 1 頁 / 共 5 頁」）
2. **Given** 使用者在第一頁，**When** 檢視分頁按鈕，**Then**「上一頁」按鈕是停用的，「下一頁」按鈕是啟用的
3. **Given** 使用者在最後一頁，**When** 檢視分頁按鈕，**Then**「下一頁」按鈕是停用的，「上一頁」按鈕是啟用的
4. **Given** 使用者在中間頁碼，**When** 點擊頁碼跳轉，**Then** 能直接跳到指定頁面

---

### Edge Cases

- **視窗極窄時**：當瀏覽器視窗縮到極窄（例如寬度 < 300px），每排至少顯示 1 張卡片，避免卡片消失或重疊
- **卡片總數很少**：當卡片總數少於一頁可顯示的數量時，不顯示分頁按鈕，或顯示「第 1 頁 / 共 1 頁」
- **API 回傳空資料**：當 API 沒有回傳任何卡片時，顯示友善的「目前沒有卡片」訊息，而非空白頁面
- **API 回傳錯誤**：當 API 發生錯誤時，顯示錯誤訊息並提供重試機制
- **載入中狀態**：在卡片資料載入期間，顯示載入指示器（loading skeleton），避免使用者看到空白或跳動的畫面
- **視窗尺寸快速變化**：使用者快速調整視窗大小時，網格重排不會造成效能問題或視覺閃爍

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須根據當前視窗寬度動態計算每排可顯示的卡片數量
- **FR-002**: 系統必須確保每一頁的每一排都填滿卡片（除了最後一頁的最後一排可能不滿）
- **FR-003**: 系統必須在視窗尺寸改變時即時重新計算每排卡片數量和每頁總數
- **FR-004**: 系統必須提供「上一頁」和「下一頁」按鈕供使用者導航
- **FR-005**: 系統必須在第一頁時停用「上一頁」按鈕，在最後一頁時停用「下一頁」按鈕
- **FR-006**: 系統必須顯示當前頁碼和總頁數資訊
- **FR-007**: 系統必須在卡片資料載入時顯示載入狀態指示器
- **FR-008**: 系統必須在 API 發生錯誤時顯示錯誤訊息
- **FR-009**: 卡片元件必須保持現有的功能（顯示 elixir cost、evolution 功能、hover 效果等）
- **FR-010**: 系統必須使用現有的 Clash Royale API 回傳的卡片資料（透過 `/api/cards` endpoint）

### Key Entities

- **Card (卡片)**：包含卡片的基本資訊
  - `id`: 卡片唯一識別碼
  - `name`: 卡片名稱
  - `iconUrls`: 卡片圖示 URL（包含一般版本和 evolution 版本）
  - `elixirCost`: 卡片的 elixir 消耗（可選）
  - `maxEvolutionLevel`: 最大進化等級（可選）
  - `maxLevel`: 最大等級
  - `rarity`: 稀有度

- **Pagination State (分頁狀態)**：管理分頁的狀態
  - 當前頁碼
  - 每排卡片數量
  - 每頁總卡片數量
  - 總頁數

- **Grid Layout (網格佈局)**：定義卡片的排列方式
  - 響應式斷點設定
  - 每排卡片數量計算邏輯
  - 卡片間距和對齊規則

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在所有常見螢幕尺寸（320px - 1920px 寬度）下，每一排的卡片都能完整對齊，沒有參差不齊的情況
- **SC-002**: 使用者調整視窗寬度時，卡片網格能在 500ms 內完成重新排列
- **SC-003**: 在桌面螢幕（≥1024px）上，每排至少顯示 4 張以上的卡片
- **SC-004**: 在手機螢幕（≤480px）上，每排顯示 2-4 張卡片
- **SC-005**: 分頁按鈕的啟用/停用狀態在 100% 的情況下都正確反映當前頁面位置
- **SC-006**: 卡片從 API 載入並顯示在頁面上的總時間不超過 3 秒
- **SC-007**: 在進行 10 次快速視窗調整時，不會出現佈局錯亂或效能問題

## Assumptions

1. **API 穩定性**：假設 Clash Royale API (`/api/cards`) 回傳的資料格式穩定，符合現有的 `CardsResponseSchema`
2. **圖片載入**：假設卡片圖片都能正常載入，若圖片載入失敗則顯示 alt text
3. **瀏覽器支援**：假設使用者使用的是現代瀏覽器（支援 CSS Grid 和 Flexbox）
4. **效能目標**：假設卡片總數在合理範圍內（< 500 張），不需要虛擬滾動（virtual scrolling）
5. **環境變數**：假設 `.env.local` 中已正確設定 `API_KEY`，用於開發和測試
6. **現有功能保留**：假設所有現有的卡片互動功能（evolution 切換、hover 效果）都需要保留
